# Dorar API request duration on Vercel Hobby

Warm browser reuse is the best improvement that works with this project's current free Vercel setup. It removes browser launch and shutdown from most requests and preserves Chrome's connections between page loads. CDN hits avoid the function and Dorar entirely.

The measurements below use real Dorar responses from protected Vercel previews on 2026-10-08. The deployed function reports 1024 MB. Project settings report `standard_legacy`, Node.js 24, and region `iad1`. No paid service, database, or always-on server was provisioned.

[Raw measurements](measurements.json) include cold samples and individual stages. [Request duration chart](request-duration.png) shows measured HTTP requests.

## Browser strategies

These are medians in seconds for two counterbalanced rounds in `iad1`, with application caches cleared before every sample. The control already loads only the main HTML document. The comparison does not measure the older implementation that loaded page assets.

| Workflow | New browser, wait for shutdown | New browser, background shutdown | Reuse open browser |
| --- | ---: | ---: | ---: |
| Hadith search, 30 results | 3.63 | 2.97 | 1.95 |
| Explanation by ID | 2.76 | 1.89 | 1.34 |
| Similar hadiths | 2.87 | 1.93 | 1.18 |
| Hadith details | 2.65 | 1.78 | 1.30 |

These times end when the service result is ready, before HTTP transfer. Two samples per cell cannot establish a percentile or guarantee. A later validation of the bounded, recoverable pool measured 2.27, 1.15, 0.98, and 1.11 seconds for the four reused-browser workflows. Its isolated search has only one warm sample because the other sample unpacked Chromium.

Browser reuse saves more than the roughly 0.2-second launch cost. In the control's search samples, median navigation fell from 2.11 to 1.36 seconds, body retrieval from 0.53 to 0.14 seconds, and cleanup from 0.44 to 0.03 seconds. Existing browser connections and process state help, but these measurements do not isolate connection reuse from ordinary upstream variation.

Background shutdown improves response time but still runs after the response. The function must finish that work. It is available as `DORAR_BROWSER_STRATEGY=background`, but reuse is the default. See [Vercel waitUntil](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package#waituntil).

## Where HTTP request time goes

The table shows individual real HTTP requests after the explanation-search parser fix. Durations are seconds. The first request used a new function instance. The following requests reused its browser.

| Part | Cold explanation by ID | Warm hadith search |
| --- | ---: | ---: |
| Browser dependency imports | 0.483 | 0.016 |
| Unpack Chromium | 5.274 | 0.000 |
| Launch or check browser | 0.281 | 0.000 |
| Create and configure page | 0.081 | 0.622 |
| Dorar navigation through DOM ready | 1.336 | 1.561 |
| Retrieve HTML body from Chrome | 0.100 | 0.121 |
| Close page | 0.059 | 0.060 |
| Decode and parse HTML | 0.225 | 0.525 |
| Other time inside API handler | 0.108 | 0.240 |
| Time outside measured handler | 0.556 | 0.572 |
| **Complete HTTP request** | **8.502** | **3.717** |

`headers` is the time until Dorar response headers arrive and is already included in navigation. It must not be added again. The outside-handler difference includes client DNS/TLS, routing, possible module initialization, serialization, and transfer. The measurements cannot divide that difference precisely among those causes. Curl's connection timers are cumulative, not independent durations.

The same preview measured similar hadiths at 1.81 seconds and details at 1.67 seconds. Cached explanation and search requests took 0.33 and 0.37 seconds. Another cold search took 12.07 seconds, including 6.46 seconds of extraction. Cold startup remains a material risk for the app's eight-second detail/explanation timeout.

## Explanation searches have a different cost

The mobile app uses `t=3` for explanation searches. Dorar now returns 15 explanation previews under `#cntnt`, without hadith IDs or narrator/grade fields. The old parser expected `#home` and returned HTTP 502.

The fix fetches the 15 linked explanation pages with at most two browser pages active at once. This restores actual hadith IDs, text, narrator, grade, and explanation text. It also reads metadata by Arabic labels because Dorar places the grade before the narrator on these pages.

A real warm API request took **16.55 seconds**: **15.00 seconds** resolving the previews, **1.12 seconds** elsewhere inside the handler, and **0.43 seconds** outside the handler. It contacted Dorar 16 times. The cached repeat took **0.24 seconds**. A later run of the prepared-binary variant took 20.43 seconds, including 17.48 seconds resolving previews; upstream performance varies. An uncached explanation search is therefore much slower than opening one explanation by ID. Parallel page timings overlap and cannot be summed as a duration breakdown.

The API returns Dorar's native 15-item page with `hasNextPage` estimated from a full page. Dorar does not provide a total in this layout. The app currently [assumes every page has 30 items](https://github.com/MAymanKH/hadithsearcher/blob/6cb77052927acb189507816aacd8a4cf38766cf9/lib/viewmodels/search_viewmodel.dart#L140), so its explanation-search pagination needs a mobile change. No mobile code was changed in this task.

## Other experiments

| Suggestion | Experiment and result | Decision |
| --- | --- | --- |
| Share duplicate work | Three simultaneous identical requests: 8.56 seconds and three browsers without sharing; 2.92 seconds and one browser with sharing | Enabled for both fetch and DOM parsing |
| Longer cache for stable IDs | Verified 24-hour in-memory expiry and CDN header for details, explanations, and similar results | Enabled; searches retain five minutes |
| Cache after app restart | CDN hits measured at 0.21–0.37 seconds; Node cache is instance-local | CDN retained; no persistent database added |
| Prefetch an explanation | Simulated a tap after five seconds: a 2.37-second fetch completed before the tap, leaving a 0.26-millisecond internal cache lookup | Not added to the mobile app; unused prefetch costs a request |
| Function nearer Dorar | `fra1` reused-browser explanation median 0.91 seconds, versus 1.34 in `iad1`; search results varied and the first regional sample was cold | Kept `iad1`; too few samples for a reliable regional decision |
| Download through Chrome without page navigation | `Network.loadNetworkResource` returned 403 in 0.25 seconds with zero results | Rejected |
| Serve a local indexed dataset | A 30-record SQLite illustration read a saved response in a fresh Python process in 45.5 milliseconds; tiny warm index queries took 0.012 milliseconds | Not a production replacement; no complete permitted dataset, and the toy Arabic search matched only one record |
| Fluid Compute on Hobby | Protected preview: cold request 5.13 seconds, normal search 2.45 seconds, explanation search 9.94 seconds | Preview only; tighter free CPU budget needs actual usage data |
| Unpack Chromium during build | Build succeeded; direct execution failed navigation. Copying the prepared files to `/tmp` worked but preparation still took 5.03 seconds and the cold request took 8.98 seconds | Rejected; no meaningful speed gain |
| Keep Chrome open 24/7 | Reused it while a function instance survived; tested a killed browser and automatic relaunch | Enabled instance reuse; Vercel controls instance lifetime |
| More browser parallelism | The existing three-browser experiment slowed down and used more resources | Limited to two pages per reused browser |

A forced browser kill recovered on the next request in 1.77 seconds. Eleven fresh explanation requests exercised automatic browser recycling. The pool recycles when idle after ten uses or when sampled Chrome RSS reaches 256 MB. Sampled Node-plus-Chrome RSS was generally about 350–430 MB in single-workflow runs. This is not a peak-memory measurement or a 500-user load test.

The [Fluid instance lifecycle](https://vercel.com/kb/guide/vercel-services-fluid-compute) documentation illustrates why a function instance is not an always-on server. This project still uses legacy compute. No warming cron was added: repeated pings consume requests and do not guarantee retention.

## Budget for 500 monthly active users

At the observed 1 GB allocation, a legacy function's duration estimate is:

```text
GB-hours = origin invocations × average complete work seconds / 3600
```

For example, 500 users making 30 API calls each is 15,000 monthly requests. With 50% CDN hits, only 7,500 requests reach the function. If 90% of those take two seconds and 10% are fresh explanation searches taking 16.5 seconds, the estimate is **7.2 GB-hours**. Adding extraction to 5% of origin calls adds about **0.55 GB-hours**. Those are assumptions, not observed user traffic. Sparse usage can produce a much higher cold-start fraction.

With no cache hits and every request a 12-second cold call, 15,000 requests use **50 GB-hours**. With every request a 24-second cold explanation search, the estimate reaches **100 GB-hours**. Explanation-search frequency and cold starts matter more than MAU alone. Background work counts toward complete work duration. Cache revalidation also invokes the function and must be included in the origin count.

Vercel's legacy Hobby allowance is 100 GB-hours and 100,000 function invocations. CDN hits avoid function invocations, although they still use CDN traffic. Other projects on the account share allowances. See [legacy function pricing](https://vercel.com/docs/functions/usage-and-pricing/legacy-pricing). The measured normal search response is about 40.6 KB. Fifteen thousand such responses transfer roughly 0.61 GB of JSON, before protocol overhead and other traffic. These estimates are not a guarantee of every platform limit or Dorar availability.

Production retains legacy compute. A protected Fluid preview used `fluid: true` through a separate configuration file. [Vercel supports this per deployment](https://vercel.com/docs/project-configuration/vercel-json#fluid), so the preview did not change production settings.

The [documented Hobby Fluid allocation](https://vercel.com/docs/functions/configuring-functions/memory) is 2 GB with at least one vCPU. The preview does not expose `AWS_LAMBDA_FUNCTION_MEMORY_SIZE`; its raw `memoryMB` is absent. That documented default is not a value measured by the benchmark.

Fluid's cold benchmark action completed in 4.31 seconds internally and 5.13 seconds including HTTP. It spent 0.24 seconds importing dependencies, 2.64 seconds preparing Chromium, 0.17 seconds launching/configuring the page, 1.00 seconds navigating, 0.17 seconds retrieving/parsing HTML, 0.02 seconds closing the page, and 0.08 seconds on other service work. The remaining 0.82 seconds occurred outside the measured service action. This cold measurement used `/__benchmark` to run the same explanation service, whereas legacy's cold HTTP measurement used the public explanation endpoint. The warm HTTP tests used identical public endpoints.

Fluid's public warm explanation search took 9.94 seconds, including 7.96 seconds resolving the 15 previews. The sampled cold process CPU was 3.87 seconds including Chrome. Warm search sampled 0.70 CPU-seconds. Explanation search sampled 8.51 CPU-seconds, but this includes overlapping Chrome measurements and overcounts the shared process. None of these process samples is Vercel's billed CPU measurement.

The [Fluid Hobby allowances](https://vercel.com/docs/functions/usage-and-pricing) are four active CPU-hours, 360 GB-hours of memory, and one million invocations. Using the conservative process samples as a planning proxy, 7,500 origin calls, 10% explanation searches, and 5% cold calls imply about **3.4 CPU-hours**. With 15,000 origin calls, the same model reaches about **6.8 CPU-hours**. All 7,500 calls cold at the sampled 3.87 CPU-seconds would imply about **8.1 CPU-hours**. These are scenario calculations, not a billing prediction. Actual overlap, Vercel accounting, and traffic mix affect the result.

Fluid produced the largest measured cold-start improvement. I left it preview-only because sparse traffic can produce cold starts and the actual cache-hit rate is unknown. The legacy setup has more room for CPU-heavy cold requests under the scenarios above. Fluid becomes a strong option once measured monthly usage supports its CPU budget.

The rejected build-time unpacking experiment is preserved in [a patch](prepacked-chromium.patch). It requires `DORAR_PREPACKED_CHROMIUM=1` on a protected preview. The deployed implementation retains runtime extraction and the original Vercel build configuration.

## Reproduce the measurements

Run `npm run check:browser` for live local endpoint validation. Run `npm run benchmark:browser` for the local strategy comparison. Both contact Dorar.

For Vercel, deploy a protected preview with `DORAR_BENCHMARK=1` and `DORAR_FETCH_MODE=browser`. Run:

```bash
npm run benchmark:vercel -- https://your-protected-preview.vercel.app /tmp/matrix.json
node scripts/benchmark-http.js https://your-protected-preview.vercel.app /tmp/http.json --preview
```

The Vercel CLI uses your existing login to access the protected preview. The HTTP script saves timings rather than authentication headers. `/__benchmark` and `Server-Timing` are enabled only with the benchmark flag. Leave that flag unset in production.

`node scripts/benchmark-browser-download.mjs` repeats the rejected browser-download experiment. `python3 scripts/benchmark-stored-data.py response.json` repeats the small local-storage illustration using a saved successful API response. It does not crawl or build a full hadith catalog.
